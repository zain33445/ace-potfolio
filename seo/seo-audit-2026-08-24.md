## Critical

### C1. `notFound()` returns HTTP 200 — soft 404s across two route families

Verified status codes:

| URL | Status | Served title |
|---|---|---|
| `/nonexistent-abc` | **200** | Not Found \| The ACE Services |
| `/projects/nonexistent-abc` | **200** | Project Not Found \| The ACE Services |
| `/foo/bar/baz` | 404 ✓ | Page Not Found \| The ACE Services |
| `/blog/nonexistent-abc` | 308 → | (redirect rule) |

Any invalid slug under `/[slug]` or `/projects/[slug]` returns **200 OK**. Only the global no-route-match case returns a correct 404.

The common factor is `generateStaticParams()`: all three dynamic routes (`/[slug]`, `/projects/[slug]`, `/services/[slug]`) declare it, and all three call `notFound()` for an unmatched param at request time — `src/app/[slug]/page.tsx:22` and `:153`, `src/app/projects/[slug]/page.tsx:102`, `src/app/services/[slug]/page.tsx:44`. That on-demand path is where the status is lost. The root `src/app/not-found.tsx` case, which never reaches a dynamic route, returns 404 correctly.

(Note: there is no `src/app/projects/[slug]/not-found.tsx`. The custom "Project Not Found" title comes from `generateMetadata` at `src/app/projects/[slug]/page.tsx:20`. The two boundary files that do exist are `src/app/[slug]/not-found.tsx` and `src/app/services/[slug]/not-found.tsx`.)

**First principle:** a status code is the only signal Google trusts for removal. A 200 on a dead URL means Google keeps it in the index and keeps recrawling it.
**Falsifiable check:** `curl -o /dev/null -w "%{http_code}" https://theaceservices.com/nonexistent-abc` must print `404`.
**Unblocks:** C2 — the three emoji URLs are only harmful *because* they answer 200.

**Status (2026-08-25): partially fixed.**

- `/projects/[slug]` and `/services/[slug]` — fully fixed. Both routes take fully-known-at-build-time params (project/service data lives in the repo, not WordPress), so `export const dynamicParams = false` makes Next.js reject any unmatched slug with a true router-level 404. Verified: `/projects/nonexistent-abc` → 404.
- `/[slug]` — the three known emoji URLs are now fixed via `src/middleware.ts`, which rejects any malformed (non-ASCII-slug) top-level path at the edge before it reaches the route. Verified: all three return 404. This closes the concrete instance and the entire bug class (any future junk slug this WordPress install produces will also 404).
- **Residual, deliberately unfixed:** a *well-formed* but nonexistent slug on `/[slug]` (e.g. `/some-deleted-post`) still returns 200. Root cause confirmed by direct testing: `/[slug]` has a co-located `loading.tsx`, which Next.js wraps in a Suspense boundary — once that boundary starts streaming, the HTTP status commits as 200 before `notFound()`'s digest resolves. This is documented Next.js behavior. Removing `loading.tsx` was tested and did not produce a clean fix in this environment (though environment flakiness on the test box makes that specific result inconclusive — it was not pursued further once the middleware fix closed the actual known cases). A durable general fix would need a real slug-existence check ahead of the render, which is a larger change than this pass covers. `/[slug]` cannot use `dynamicParams = false` the way the other two routes did — it resolves live WordPress posts, and the sitemap deliberately revalidates hourly so new posts become reachable without a redeploy; forcing `dynamicParams = false` there would 404 every new post until the next full rebuild.

### C2. Three noindexed soft-404 URLs are being actively submitted in the sitemap

```
/%f0%9f%8f%a8-hotel-development-services-in-usa-...
/%f0%9f%a7%ae-quantity-surveyor-services-in-usa-...
/%f0%9f%8f%97%ef%b8%8f-warehouse-development-in-usa-...
```

Each: **HTTP 200**, 22 words of body content, `noindex`, canonical pointing at the **homepage**, and the homepage's `<title>`. These are percent-encoded emoji slugs from WordPress that fail lookup in `src/app/[slug]/page.tsx:153`.

Submitting a noindexed URL in a sitemap is a directly contradictory signal, and canonicalising three dead URLs to the homepage points junk equity at the most important page on the site.

**Root cause:** `src/app/sitemap.ts:50-56` maps `getPosts()` output straight to sitemap entries with no filter for slugs the `[slug]` route can actually resolve.
**Falsifiable check:** all three URLs return 404, and `curl -s .../sitemap.xml | grep -c '%f0'` returns `0`.

## High

### H0. An entire orphaned page tier — 28 live, indexable pages in no sitemap and no internal link

**This is the largest finding in the audit and it was not visible until the WordPress page list was cross-checked against the live site.**

The WP install holds 47 pages. 28 of them resolve on the public site at HTTP 200, are fully indexable (no `noindex`, self-canonical), carry 400–2,113 words of real content — and appear in **neither `sitemap.xml` nor any internal link on the site**. Verified individually, with redirect-following, so these are genuinely live self-URLs and not 301s (`/samples` was the only slug that already redirects, to `/projects`).

**Tier A — commercially valuable, 900–2,100 words each (20 pages):**
`/outsourcing-estimation` (2,113w) · `/electrical-estimation` (1,717w) · `/community-parks` (1,098w) · `/educational-buildings` (1,078w) · `/hotels-development` (1,074w) · `/building-estimating` (1,073w) · `/freelance-estimation` (1,067w) · `/healthcare-buildings` (1,063w) · `/blueprint-estimation` (1,052w) · `/residential-buildings` (1,041w) · `/bridges-construction` (1,038w) · `/industrial-construction` (1,016w) · `/warehouses-development` (1,011w) · `/office-development` (996w) · `/quantity-surveyor-services` (970w) · `/assembly-buildings` (967w) · `/residential-construction` (960w) · `/commercial-construction` (955w) · `/construction-estimation` (904w) · `/structural-services` (882w)

**Tier B — too thin to rank as-is (4 pages):**
`/shopping-centre` (513w) · `/industrial-estimating` (466w) · `/commercial-estimation` (437w) · `/residential-estimating` (425w)

**Tier C — junk that should not be indexable at all (4 pages):**

| URL | Words | Problem |
|---|---|---|
| `/home` | 502 | **A second, indexable, self-canonical homepage.** Direct duplicate-content competitor to `/` |
| `/terms-conditions` | 575 | Duplicate of `/terms-and-conditions`, which is the one in the sitemap |
| `/sample-page` | 532 | WordPress default boilerplate |
| `/email-marketing-expert` | 401 | An internal job posting, publicly indexable |

**Why this matters more than anything else here.** The 2026-08-19 audit recorded an unexplained GSC cluster — "warehouse/hotel/education development services, quantity surveyor, freelance estimating" drawing impressions at positions 15–90 for pages not in any content strategy doc. **These are those pages.** The site already owns ~20 topically-focused service pages that Google has found on its own and is ranking on page 2–3, entirely without sitemap inclusion or a single internal link.

They also hold essentially all of the site's non-homepage link equity. Of 529 referring domains, the homepage takes 529; the only other URLs with any referring domains at all are orphans:

| Orphan URL | Referring domains | URL Rating |
|---|---|---|
| `/warehouses-development` | 4 | 4.5 |
| `/outsourcing-estimation` | 2 | 4.7 |
| `/quantity-surveyor-services` | 1 | 4.7 |

`/warehouses-development` is also the site's **only non-branded organic ranking** (#1, `warehouse development program`).

**First principle:** a page Google ranks at position 15–90 with zero internal links and zero sitemap presence is not a weak page — it is a page competing with one hand tied. Internal linking and sitemap inclusion are the cheapest ranking inputs available, and these pages currently get neither.
**Falsifiable check:** all Tier A pages appear in `sitemap.xml` and are reachable within 2 clicks of the homepage; all Tier C pages return 301 or carry `noindex`.
**Leading indicator:** GSC → Performance, filter to these URLs. If average position improves after they gain sitemap + internal links, the constraint was discoverability. If it does not move in 6 weeks, the constraint is page quality and they need content work, not plumbing.
**Note:** `cms.theaceservices.com` is correctly protected (`Disallow: /` plus `noindex, nofollow`), so the orphans are not a subdomain duplication problem — they are live on the primary domain.

### H1. Keyword cannibalization — 16 posts competing across 3 topics

| Topic | Competing posts | Words each |
|---|---|---|
| Warehouse development | **6** | 1,417–1,599 |
| Blueprint estimation | **6** | ~1,400–1,700 |
| Quantity surveyor | **4** | ~1,400–1,700 |

All 16 are live, indexable, and near-identical in intent. The warehouse set alone:

- `/warehouse-development-services-in-usa`
- `/warehouse-development-services-in-usa-building-efficient-spaces-for-modern-businesses`
- `/warehouse-development-services-in-usa-building-efficient-scalable-and-modern-storage-solutions`
- `/end-to-end-warehouse-development-services-for-modern-businesses`
- `/warehouse-development-services-how-warehouses-are-planned-designed-and-built`
- `/why-your-business-needs-a-professional-warehouse-development-company`

Commit `5f44284` ("301 redirects for consolidated duplicate blog posts") only covered 3 URLs — `next.config.js` redirects `*-2` suffixed duplicates. The real duplication is these semantic near-clones, which were never touched.

**First principle:** six pages splitting the same intent means Google picks one arbitrarily and dilutes link equity six ways. This is not a lack of content — it is an excess of undifferentiated content.

**Backlink check changes the plan.** Ahrefs `pages-by-backlinks` confirms **not one of the 16 posts has a single referring domain.** There is no link equity to preserve, so the choice of redirect target is unconstrained — which means the right targets are not among the 16 at all. They are the H0 orphans, which already hold the links, the clean keyword-matching slugs, and (for warehouse) a #1 ranking:

| Cluster | Dupes | Recommended 301 target | Why |
|---|---|---|---|
| Warehouse development | 6 | `/warehouses-development` | 4 refdomains, UR 4.5, ranks #1 for `warehouse development program` |
| Quantity surveyor | 3* | `/quantity-surveyor-services` | 1 refdomain, UR 4.7, exact-match slug |
| Blueprint estimation | 6 | `/blueprint-estimation` | 1,052w orphan, exact-match slug, no competing dupe |

\* `/quantity-surveyor-vs-cost-estimator-key-differences` is a genuine comparison-intent post, not a fourth "QS services" page. It should stay live and link to the target rather than redirect into it.

This makes H0 and H1 one piece of work rather than two: consolidating the blog dupes *into* the orphan pages fixes the cannibalization and wires up the orphan tier in the same pass.

**Sequencing:** must happen BEFORE any new content investment, or new pages join the same pile-up.
**Falsifiable check:** after consolidation, each topic has exactly one indexable URL; the rest 301 to it. Re-pull `site-explorer-organic-keywords` in 6 weeks — if the surviving URLs still rank nowhere, cannibalization was not the binding constraint and the problem is authority (DR 14), not architecture.
**Leading indicator:** GSC → Performance → filter by "warehouse development", watch whether impressions consolidate onto one URL.

### H3. One blog post renders 59 `<h1>` tags and leaks the CMS hostname

`/state-to-state-construction-estimation-services-why-u-s-contractors-trust-the-ace-services` wraps every paragraph in `<h1>`. Sample:

> H1: "In the competitive world of construction, accuracy, efficiency, and trust define success."
> H1: "At The ACE Services (**cms.theaceservices.com**), we've built our reputation as..."

Two problems: the heading hierarchy is meaningless to Google, and the published body copy exposes the internal headless-WordPress hostname to readers and crawlers. The title is also wrapped in literal curly quotes, which will render in the SERP.

This is Elementor HTML passed through unsanitised — the known constraint that WP page bodies are Elementor blobs. Every other page on the site has exactly 1 H1 (95/99).

**Falsifiable check:** page has exactly 1 `<h1>`; grep for `cms.theaceservices.com` on rendered blog HTML returns 0.

### H4. 38 project pages have meta descriptions of 198–272 characters

Every `/projects/*` page overshoots the ~160-char SERP limit — worst case `/projects/cardin-place-eagleville` at 272. All will truncate mid-sentence. These are generated from a shared template, so this is one fix, not 38.

**Falsifiable check:** no page has a description over 160 chars.

## Low / Info

- **No `llms.txt`.** `/llms.txt` returns 200 serving the Next.js app shell rather than a text file. Given DR 14 and near-zero AI-surface presence this is low-value, but it is also nearly free.
- **5 pages carry FAQPage schema** (homepage + 4 service pages). Google retired FAQ rich results for all sites on 2026-05-07, so this earns no SERP feature. **Informational only — do not remove it**; the markup is harmless and the Q&A content is genuinely useful. Just don't add FAQPage to new pages expecting a SERP benefit.
- **Schema is a genuine strength.** All 99 pages carry `ProfessionalService`, `Organization`, `WebSite`, `PostalAddress`, `OpeningHoursSpecification` and `OfferCatalog`; 87 carry `BreadcrumbList`; 45 blog posts carry `Article`. The only 3 pages missing `Article` are the C2 soft-404s.
- **Security and delivery headers are correct.** HSTS with preload, full CSP, `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`. `x-nextjs-cache: HIT` at the Cloudflare edge; TTFB 0.41s homepage, 0.77s `/cost-estimating`.
- **Image alt coverage 449/450 (99.8%)** across the whole crawl — one intentional empty alt.
- **`robots.txt` is correct**, and `/admin` + `/admin-login` are properly disallowed.
